# Правила проекта

Интерактивный прототип по Figma-макетам. Стек: Next.js 15 (App Router), React 19,
глобальный CSS. Порт — 3001 (3000 занят чужим проектом). Работа с макетом — через
Figma MCP (файл `HL4PatufFZkyPKtx3LGivP`), эталоны и design context кешируются в `.figma/`.

## Процесс: сначала раунд анализа

Перед разработкой любой фичи — короткий раунд анализа (зафиксировать в
HANDOFF/ответе, а не только в голове):

1. **Зачем** это нужно пользователю и что он увидит; какое поведение
   считается правильным.
2. **Как это работает в реальном продукте** (а не «как проще нарисовать»):
   что такое скелетон, загрузка, сессия, навигация — по смыслу.
3. **Как проверим**: какой сценарий/кадры/замеры докажут результат.
4. Только потом — код. Не «делать как получается», а сначала понять модель.

Если фича ломает ранее зафиксированное поведение — сначала восстановить
инвариант, потом улучшать.

## Иконки: только SVG нужного цветового варианта из Figma

Интерфейсные иконки никогда не raster (никаких PNG/WebP для иконок — только растр
для иллюстраций, аватаров, фото и брендовых артов). Правильный вариант берём так:

1. **Не брать глиф из общего design context компонента.** Контекст библиотечного
   компонента (кнопка, filter-tag, addon и т.п.) отдаёт дефолтный вариант глифа —
   часто это акцентный цвет (`#0024E1`) или плейсхолдер, а не тот цвет, что в макете.
2. **Вызывать `get_design_context` на конкретном инстансе во фрейме** (id из
   `get_metadata` корневого узла), с `disableCodeConnect: true`. В ответе
   `const assetPathPrefix` + константы ассетов — это варианты именно этого инстанса.
3. **Использовать ассет, который реально рендерится в коде ответа** — обычно
   `imgFixer` (глиф, подставленный в слот). Остальные `img*` — соседние варианты
   компонента; скачивать их смысл есть только чтобы сверить цвет.
4. **Сверить цвет с эталоном** (`.figma/main/reference-full.png`, crop через `sips`)
   до подключения. У глифов Альфы фиксированные заливки: `#030306` (primary),
   `#747474` (secondary), `#CCCCCC`/`#DCDCdd` (tertiary), `#0024E1` (accent),
   white для тёмных кнопок. Если в макете иконка на тёмном фоне — брать белый
   вариант (у support-кнопки он лежит отдельным ассетом рядом с фиолетовым).
5. **IconView-иконки (балансы, аватары, знаки)** собираются из трёх частей:
   маска-фигура (`imgShapeContent`, используется как CSS mask, её цвет не важен),
   сплошная заливка `BgColor`/`BgImg` (цвет/фото берутся с узла конкретного
   инстанса: `get_design_context` на `<node>;448:17360` / `...;448:17392` —
   иначе придёт плейсхолдер) и глиф по центру (`imgFixer`).
6. Скачанные SVG кладём в `public/assets/figma/` под семантическими именами
   (`filter-icon.svg`, `mail-icon.svg`), ссылкаем напрямую. Корневые width/height
   в SVG не трогаем, размеры задаём обёрткой.

### Цвет иконки: заливка файла + пиксельный замер, а не «номер варианта»

Цвет иконки — это **заливка внутри SVG**, а не имя компонента и не подпись
варианта. Порядок, который даёт верный цвет с первого раза:

1. `get_metadata` корневого фрейма → находим инстанс-контейнер блока →
   `get_design_context` **на этом инстансе** с `disableCodeConnect: true`.
   В ответе у каждого инстанса есть `imgFixer` — ровно тот ассет, что нарисован.
2. Скачать `imgFixer*` через `curl -L` (ссылки живут 7 дней) и посмотреть
   заливку: `grep -oE '(fill|fill-opacity)="[^"]*"' file.svg`.
3. Ожидаемые комбинации у глифов Альфы: `fill="#030306" fill-opacity="0.88"`
   (= `--text-primary`, rgba(3,3,6,.88)), `#747474` (secondary),
   `#CCCCCC`/`#DCDCDD` (tertiary), `#0024E1` (accent), `#FFFFFF` на тёмном.
   Акцентный `#9032EE`/`#0024E1` там, где макет серый или почти чёрный, —
   признак того, что взяли **дефолтный вариант глиф-компонента**, а не инстанс.
4. Сверить **пикселем**, а не глазом: `get_screenshot` узла с
   `maxDimension: 1600` (нативный размер) → замерить цвет в иконке; затем тот же
   замер на своём рендере. Эффективный цвет = заливка с учётом `fill-opacity`
   поверх фона: `#030306` @ .88 на `#f2f3f5` → `#202123`. Разница 1–2 единицы
   нормальна (α), заметно другой цвет = не тот вариант.

Что нельзя:

- Брать ассет из док-блоков ответа (строки вида `Size=24, Style=Line,
  Color=False`, Node `1:3867`) — это спецификация глиф-компонента, а не то, что
  стоит в слоте. Так на `/login` три иконки стали фиолетовыми `#9032EE`, а
  «Телефон» серой `#747474` вместо `#030306` @ .88 у всех четырёх; тем же
  способом «звук» на `/welcome` получил `#747474` (верный инстанс `1:4739`
  отдаёт `#030306` @ .88). Разбор — `HANDOFF.md`, «Иконки входа: цвета
  (05.11.2026)».
- Перекрашивать instance-глиф CSS-маской: `fill-opacity` умножается на альфу
  маски и иконка бледнее макета (.88 → .774). Такие иконки подключаем `<img>`,
  как в макете.
- «Чинить» цвет правкой/удалением `fill-opacity` в файле: hex совпадёт, а
  плотность красного станет как у сплошной заливки — макет плотнее не станет.
- Полагаться на parity/`verify`: расхождение цвета четырёх иконок 24 px —
  это ~0.2 % пикселей, пороги его пропускают (так и случилось, паритет
  страницы был 0.85 %).

## Состояния и контент

Не придумывать элементы, данные и состояния, которых нет в переданном макете:
никаких toast, выдуманных ответов ассистента, дополнительных пунктов меню или
операций. Интерактив только на контролах, оправданных макетом (табы, поиск
по существующим операциям, чекбоксы, сдвиг карусели). Выпадающий список
«Дела в работе» убран по просьбе пользователя (05.11.2026): чипса «Дела в
работе» и пункт «Разобрать» — некликабельные (см. HANDOFF, «Дела в работе:
дропдаун убран»).

Единственное исключение — **скелетон загрузки обеих главных**, добавлен по
просьбе пользователя: состояния `?skel=off` / `?skel=hold` / `?skel=on` и
автоотключение в headless — это QA-обвязка, а не новое продуктовое
состояние. Скелетон теперь **прогрессивный по виджетам** (не один общий
оверлей): у каждого блока своя плитка-скелетон, она прячется ровно в момент,
когда приходит контент этого блока; контент скрыт (`visibility: hidden`) до
этого момента, сетка не дёргается. Расписание — в
`lib/skeleton-widgets.ts`; `DashboardSkeletonGate` ведёт классы
`body.sk-loaded-<виджет>` и снимает fallback только после последнего
виджета. См. HANDOFF, «Скелетон: прогрессивная загрузка по виджетам». Не
возвращать «общий скелетон + ступенчатое появление пустых секций».

Высота сцены табов меняется **мгновенно вместе с подменой контента** (без
анимации `height`); анимируются только opacity/filter/transform контента —
см. HANDOFF, «Высота сцены табов».

## Первый вход и reload

- Состояние входа живёт в `sessionStorage` ([lib/entry-session.ts](lib/entry-session.ts)):
  обычный reload (Cmd+R / F5) сессию сохраняет и показывает дашборд — первый
  вход не перезапускается.
- **Первый вход открывается только при hard reload (Cmd+Shift+R) или при
  первом заходе в новой вкладке.** Сервер отличает hard reload по заголовкам
  запроса документа (`lib/reload-mode.ts`): Chrome/Edge присылают
  `cache-control: no-cache` + `pragma: no-cache` у hard reload и
  `cache-control: max-age=0` у обычного reload; навигация по ссылке
  заголовков не несёт. Страницы `/` и `/accountant` читают это через
  `headers()` и передают `hardReload` в `DashboardSkeletonGate`, который
  чистит сессию и уводит на `/login`.
- Нет сессии (новая вкладка, прямой заход, после «Выйти») — сразу `/login`,
  без мигания скелетона.
- Тесты и скриншоты могут подставить `window.__alfaEntryState` — это значение
  имеет приоритет над sessionStorage.

## Имя клиента (модалка по «/»)

- Полное имя клиента — клиентский store `lib/client-name.ts`
  (`localStorage.__alfaClientName`, фолбэк в память). Дефолт —
  «Набокова Анна Дмитриевна».
- На дашбордах (`/` и `/accountant`) клавиша «/» открывает модалку
  «Имя клиента» (макет `136:21612`); в полях ввода/`contenteditable`
  хоткей не срабатывает.
- Производные не дублировать в разметке: приветствие — только имя,
  подпись в шапке — «Фамилия И.О.» (инициалы из имени и отчества).
- Фича обязана оставаться чисто клиентской (localStorage, события) — без
  серверных вызовов, чтобы переноситься в статическую сборку.

## Счётчик «2» на «Сводке»

Логика исходная и не «вкладочная»: пока «Сводка» не открыта, бейдж «2»
остаётся в шапке табов (ширина 585); при открытии «Сводки» идёт таймер
**3 s** → бейдж гаснет за 0.22 s и снимается, шапка сужается (556/558/559 по
активной вкладке). Уход с вкладки раньше 3 s отменяет отсчёт, при возврате
он начинается заново. Не менять на «скрывать при уходе с Ассистента» —
это уже ломало поведение (см. HANDOFF, «Счётчик «2»: возврат 3-секундной
логики»).

## Плашка ассистента и табы

- Нижняя плашка на обеих главных — один компонент
  `components/chrome/AssistantBar.tsx`: полоса 6 px, угловые вырезы
  (page-bg поверх контента, чтобы не просвечивал острый угол), логотип по
  центру, подпись. На бухгалтере по просьбе пользователя подпись
  **Alpha Intellect** и кнопка «Связь с банком» — это отступление от
  инстанса `136:19073`, отмечено в HANDOFF.
- Шапка табов — строго 52 px (`height/min/max`, `flex: none`); при
  исчезновении счётчика она не смещается по вертикали (`.tabs-compact` без
  `translateY`). Аккаунт/контент не должен менять её высоту.
- Табы бухгалтера («С чего начать», «Сводка» и др.) — некликабельные:
  никаких active-переключений и текста по клику.
- Имя клиента нормализуется с заглавной буквы в каждом слове (включая
  дефисные части) и в приветствии, и в подписи шапки.

## Вёрстка

- Тени (drop-shadow) рвутся об `overflow: hidden`. Глобально стоит
  `box-sizing: border-box` — padding вьюпорту не помогает (клип идёт по border box);
  давайте тени место через реальную высоту + компенсирующий отрицательный margin
  (см. `.tasks-viewport`: высота 240 = 212 контента + 28 на тень, `margin-bottom: -28`).

## Ширина контейнеров дашбордов

Она **фиксированная**, не full-bleed: главная предпринимателя — колонка
**972 px** («Основа» макета `59:16843`), главная бухгалтера — **максимум
1248 px** (`.cur-content` из @Main). На широких экранах (>1600) контент не
растягивать: колонки центрируются в зоне справа от сайдбара базовым CSS.
Скелетоны обязаны использовать те же контейнеры, чтобы переход
«скелетон → контент» не двигал сетку.

## Статическая сборка (открытие файла без сервера)

Прототип должен быть доступен как статический файл: `npm run build:static`
собирает `static-dist/` — её открывают двойным кликом по `index.html`
(`file://`), без Node и HTTP-сервера. Правила, чтобы не сломать:

- Статика — отдельный бандл (`static/entry.tsx` через esbuild), Next-страницы
  с `headers()` в неё не входят; `next/link`/`next/navigation` подменяются
  hash-роутером `static/shims/*`.
- Пути к ассетам в бандле и CSS относительные; CSS-ссылки (`url(assets|fonts)`)
  инлайнятся в data-URI, иначе маски/шрифты блокируются CORS в file://.
- Новый код не должен тянуть серверные Next API в клиентские компоненты —
  иначе статическая сборка отвалится.
- Проверка обязательна: открыть `static-dist/index.html` в headless Chrome
  **без** `--allow-file-access-from-files`, пройти вход → роль → setup →
  главную, переключить вкладку, открыть модалку «Имя клиента», проверить
  `#/accountant`; не должно быть failed requests и ошибок консоли.

## Проверки после правок

- `npm run lint` (должен быть чистым, `--max-warnings 0`).
- `npm run verify http://localhost:3001` — сервер должен быть запущен.
- Скриншот 1600×900 headless Chrome и parity против эталона: главная —
  `.figma/main/reference-full.png`, бухгалтер — `.figma/accountant/reference-full.png`
  (актуальный фрейм `136:18883`).
- У главных прогрессивный скелетон по виджетам: полсекунды виден полный
  скелетон, затем каркас (620 мс), табы/hero (720/840), «Мои дела» (1200),
  лента (1550); у бухгалтера 620…1500 мс. `?skel=off` — сразу контент;
  `?skel=hold` — скелетон держится; `?skel=on` — расписание даже в headless.
  Скелетон блока обязан совпадать с живым по метрикам текста (16/20, 14/18),
  иначе блок «прыгает» при подмене.
- `npm run build:static` — статическая сборка; проверять открытием
  `static-dist/index.html` через file:// (без HTTP-сервера) по сценарию из
  раздела «Статическая сборка».
- Не запускать `next build` при живом `next dev` (общий `.next`).
