# Альфа-Бизнес — Ассистент — Handoff

> Заполняется по ходу работы. Каркас — из alfa-mcp.

Интерактивный прототип по Figma-макету. Стек: Next.js 15 (App Router),
React 19, TypeScript. Без UI-библиотек, глобальный CSS.

## Запуск

```bash
npm install
npm run dev -- --port 3001   # dev-сервер :3001 (порт 3000 занят чужим проектом)
npm run build                # прод-сборка. НЕ запускать при живом dev (общий .next)
npm run start -- --port 3001 # прод-сервер
npm run verify http://localhost:3001  # parity-QA (сервер должен быть запущен)
```

## Адаптив 4K / широкие экраны

**Контейнеры дашбордов фиксированные** (правка по просьбе пользователя):
- главная **предпринимателя** — колонка **972 px** (как «Основа» в макете
  `59:16843`), на любой ширине;
- главная **бухгалтера** — **максимум 1248 px** (как `.cur-content` в @Main),
  на любой ширине.

Обе колонки центрируются в свободной зоне справа от сайдбара; это даёт базовый
CSS — `.dashboard-content` с `margin-left: max(336px, calc(50vw - 328px))` и
`.cur-content` с `max-width: 1248px; margin: 0 auto`. `styles/wide.css` больше
не растягивает контент: прежний full-bleed подход (колонка на всю ширину,
сетка карточек на 6 колонок, растянутые фильтры/аналитика/табло) **отменён** —
это была моя ошибка в адаптивном проходе. Файл оставлен пустым по правилам
(комментарий-политика), чтобы не менять порядок подключения стилей.

Скелетоны повторяют ту же фиксированную сетку: их контейнеры используют те же
`.dashboard-content` / `.cur-content`, поэтому на 1920/3840 они остаются
972 / 1248 и переход «скелетон → контент» не двигает макет.

Проверено: 1600×900 не изменился (главная, табы, бухгалтер — прежний паритет);
1920 и 3840 — контейнеры `972` (`x=472/632/1592`) и `1248`
(`x=300/460/1420`), скелетон совпадает с контентом. Скриншоты:
`.figma/qa/shots/fixed-4k-dashboard.png`,
`fixed-4k-accountant.png`, `fixed-4k-dashboard-skeleton.png`.

Онбординг (логин/роль/настройка) остаётся 1600-й центрированной композицией на
полноэкранном фоне — это не затронуто.

### Счётчик «2»: возврат 3-секундной логики (05.11.2026)

Восстановлено исходное поведение (`Glavnaya.tsx`):

- Пока «Сводка» не открыта — бейдж «2» остаётся (на «Ассистенте» и других

- Открыли «Сводку» — стартует таймер **3 s**; по истечении бейдж гаснет
  (`.hiding`, opacity 0 за 0.22 s ease-in) и снимается, шапка сужается
  (компакт-ширины по активной вкладке: 556/558/559), капсула ведётся
  покадрово.
- Ушли с «Сводки» раньше 3 s — таймер снимается, при возврате отсчёт
  начинается заново.
- `prefers-reduced-motion`: переключение мгновенное (guard как раньше).

Проверено программно: старт — бейдж есть, 585; открыли «Сводку»: +0.3 s —

### Стабильное появление подложки вкладки

Белая подложка должна появиться один раз после выбора и двигаться вместе
с кнопкой, пока шапка сужается. При переходе со «Сводки» после снятия

Сверяем старт и завершение анимации, быстрые переключения, сужение
шапки и мгновенную смену при reduced motion.

Подложка теперь псевдоэлемент активной кнопки. Её размеры задаёт сама
кнопка. В Chromium и WebKit при сужении 585→556 px непрозрачность
подложки оставалась равна 1, а шапка сохраняла y=120 и высоту 52 px.
При быстрых переключениях зарегистрировано по одному старту анимации
на выбор. Тест офлайн-сборки поймал прежний запуск через 687 мс.

### Первый вход: только hard reload (05.11.2026)

Было: состояние входа жило в памяти документа (`window`), поэтому **любой**
reload (и Cmd+R, и Cmd+Shift+R) начинал с `/login`. Просьба: первый вход
показывать только при hard reload, обычный refresh — просто обновлять
дашборд.

Сделано:

- `lib/entry-session.ts` — состояние входа перенесено в **sessionStorage**
  (вкладка его переживает обычный reload); подстановка
  `window.__alfaEntryState` из тестов сохранена и имеет приоритет.
- `lib/reload-mode.ts` — сервер отличает hard reload по заголовкам запроса
  документа: Chrome/Edge шлют `cache-control: no-cache` + `pragma: no-cache`
  при hard reload и `cache-control: max-age=0` при обычном; навигация по
  ссылке заголовков не несёт. Замерено на живом dev-сервере через временный
  `/api/headers` (после проверки удалён):
  обычный reload → `{"cacheControl":"max-age=0"}`,
  hard reload → `{"cacheControl":"no-cache","pragma":"no-cache"}`.
- `/` и `/accountant` — серверные страницы читают `isHardReload()` через
  `headers()` и передают `hardReload` в `DashboardSkeletonGate`. Гейт при
  `hardReload` чистит сессию и уводит на `/login`; без сессии (новая вкладка,
  прямой заход, после «Выйти») тоже сразу `/login` — без мигания скелетона.
  Побочный эффект: эти два роута стали динамическими (SSR по запросу) — иначе
  заголовки reload не прочитать.

Проверено программно (CDP): вход в сессию → дашборд; **обычный** reload —
остаёмся на дашборде; **hard reload** — `/login`; свежая вкладка — `/login`;
«Выйти» — `/login` и сессия сброшена; полный сценарий
`/welcome → /setup → /` работает.

### Скелетон: прогрессивная загрузка по виджетам (05.11.2026)

**Было (неправильно):** один общий скелетон висел 700 мс, затем снимался
целиком, и уже после этого секции появлялись ступенями. Получалось, что
серые плитки исчезают раньше, чем приходит контент: скелетон и элементы
жили вразнобой, «имитация загрузки» читалась как кривая анимация.

**Анализ.** Скелетон — это плейсхолдер **конкретного виджета**. В реальном
продукте он исчезает в момент прихода данных этого виджета, а не по общему
таймеру всей страницы. Значит нужен не «экран загрузки», а набор
независимых плиток со своими моментами готовности: пока виджет грузится —
на его месте скелетон; пришёл — скелетон этой плитки исчезает, контент
появляется. Чужие виджеты при этом не ждут.

**Сделано:**

- `DashboardSkeletonGate` больше не снимает оверлей целиком: он ведёт набор
  классов `body.sk-loaded-<виджет>` по расписанию из страницы
  (`lib/skeleton-widgets.ts`) и убирает fallback только когда готовы все.
- Контент виджета скрыт (`visibility: hidden`) в своей геометрии, пока нет
  его класса; скелетон-плитка того же виджета прячется в тот же момент.
  Оба слоя занимают одну и ту же сетку — сдвигов и «пустых кадров» нет.
- Регионы скелетона: главная — sidebar, topbar, spotlight, tabs, hero,
  «Мои дела», лента; бухгалтер — qa, balance, inwork, banners, tablo,
  cards, feed (первый ряд скелетона разбит на три отдельные плитки).
- Расписание (мс от маунта): предприниматель — shell/spotlight 620,
  tabs 720, hero 840, «Мои дела» 1200, лента 1550; бухгалтер — qa 620,
  balance 760, inwork 900, banners 1020, tablo 1180, cards 1320, feed 1500.
  По просьбе пользователя загрузка удлинена на 0.5 s (раньше «мигала»):
  полсекунды виден полный скелетон, затем по виджетам приходит контент.

### Статика HTML: нужен ли Node

Сейчас проект — Next.js 15 (App Router) с серверным рендером: `npm run dev`
или `npm start` (Node), либо деплой, который поднимает Node/SSR. Просто
открыть «html» из сборки нельзя — в `.next` нет готовых `index.html` для
двойного клика.

Даже `output: "export"` (статический экспорт Next) не даёт «открытие
файла двойным кликом»:
- ассеты и чанки ссылаются абсолютно (`/_next/...`, `/assets/...`), из
  `file://` они не находятся;
- клиентский роутер Next догружает RSC-данные по HTTP — из `file://`
  браузер блокирует такие запросы (CORS);
- hard reload сейчас различается по заголовкам запроса документа на
  сервере (`lib/reload-mode.ts`) — без Node это не работает;
- `headers()` в страницах делает `/` и `/accountant` динамическими — для
  `export` их нужно переписать.

Статический экспорт **можно** сделать, но запускать придётся через любой
HTTP-сервер (`python -m http.server`, `npx serve`, Vercel/Netlify), а не
двойным кликом.

Чтобы работало именно **открытие HTML с диска**, нужен отдельный
статический билд (не Next): плоские html-страницы, относительные пути к
ассетам/шрифтам, обычные `<script>` (модули из `file://` браузеры режут по
CORS), навигация — обычными ссылками, а не клиентским роутером; hard reload
заменяется на правило «новая вкладка/выход/`?reset`». Фича имени клиента к
этому готова: она полностью клиентская (localStorage + события, без
серверных вызовов), модалка перенесётся 1:1; в Chrome/Edge/Firefox
localStorage на `file://` работает, в Safari может быть заблокирован — для
этого уже есть фолбэк в памяти.

### Статическая сборка под file:// (npm run build:static)

Зачем: прототип должен открываться двойным кликом по HTML, без сервера.

Почему не `next build` / `output: export`: Next ссылается на чанки
абсолютными путями `/_next/...`, клиентский роутер догружает RSC по HTTP, а
из `file://` такие запросы блокируются; плюс страницы используют серверный
`headers()` для hard reload.

Как устроено (`scripts/build-static.mjs`):

- React-прототип бандлится **esbuild** в один `app.js` (IIFE, classic
  script: ES-модули из file:// браузеры режут по CORS);
- `next/link` и `next/navigation` подменяются hash-роутером
  `static/shims/*`: `#/`, `#/accountant`, `#/login`, `#/welcome`, `#/setup`;
  навигация, back/forward — через hash, без сервера;
- CSS склеивается в `app.css`; все `url(assets|fonts)` инлайнятся в
  data-URI (маски и шрифты в file:// грузятся CORS-запросом и иначе
  блокируются — проверено на Chrome без `--allow-file-access-from-files`);
  пути к картинкам в JS переводятся из `/assets/...` в относительные
  `assets/...`;
- ресурсы разметки копируются рядом с `index.html`. Шрифты и несколько
  крупных фонов, используемых только в CSS, уже встроены в `app.css`;
- при отсутствующем CSS-ресурсе сборка завершается с именем таблицы стилей
  и путём до файла;
- `index.html` — `<script src="app.js">` и `<link rel="stylesheet">`.

Результат: `static-dist/` (8,8 МБ) и `static-dist.zip` (7,8 МБ).
Распакуйте архив целиком и откройте `static-dist/index.html` двойным
кликом: первый вход как в прототипе (логин → выбор роли → setup →
главная), сессия в sessionStorage, имя клиента в localStorage, бухгалтер —
`index.html#/accountant`, QA-флаги `?skel=off|hold|on` работают.

`npm run verify:static` распаковывает ZIP во временную папку и открывает
`index.html` в Chromium через `file://`. Проверяет вход, вкладки, фокус
и сохранение имени, смену ролей, скрытие и показ сумм, выход и возврат
на вход при прямом открытии защищённого маршрута. Тест также отслеживает
ошибки консоли, загрузку картинок и шрифта, попытки HTTP-запросов.
CI использует Node.js 22 и `npm ci`, выполняет этот тест без HTTP-сервера
и сохраняет проверенный ZIP в артефактах запуска.

Ограничения статики: hard reload неотличим от обычного (нет серверных
заголовков) — первый вход сбрасывается кнопкой «Выйти», новой вкладкой или
